# Hardware Standard — Meta Supreme Apex Genesis

**Updated:** 2026-08-12

Reference classes, not shopping lists. A class is defined by the work it must
finish without the operator waiting on it. Parts age out within a year; the
obligation does not.

This system has three surfaces with genuinely different demands: the **web
app**, which needs nothing in particular; the **API**, which is bounded by
Postgres and by whichever model provider is answering; and **pgvector**, which
is the only component whose sizing is worth arithmetic.

---

## 1. Web (`apps/web`)

Next.js static-first. Nothing here justifies a hardware requirement — the
Council runs server-side and the browser renders text and layout.

A five-year-old laptop is a legitimate operator machine, and that is deliberate:
an intelligence system that demands a workstation to *read its output* has
misplaced the work.

## 2. API (`apps/api`)

FastAPI, async throughout. The bottleneck is almost never CPU.

| Class | Purpose | Floor |
|---|---|---|
| **Bench** | Single operator, offline flagship path, no database | 2 cores / 4 GB |
| **Line** | Team use, Postgres attached, live providers | 4 cores / 8 GB / SSD |
| **Room** | Multi-tenant, concurrent councils, embedding backfill | 8+ cores / 16 GB / NVMe |

**Concurrency is bounded by the provider, not the box.** A council deliberation
is eight-plus model calls; wall-clock is provider latency, and the process is
idle for nearly all of it. Adding cores to make deliberation faster is the wrong
purchase — it is not compute-bound. Raise the async concurrency limit and the
provider rate limit instead.

The zero-key offline path (`standalone_api.py`, `make standalone`) runs
comfortably inside Bench and needs no database. That path is the canonical CI
target for good reason: it is the one that can be verified anywhere.

## 3. Postgres + pgvector

The only component where sizing is arithmetic rather than judgement.

**Index memory is the number that matters.** An HNSW index wants to live in RAM;
once it spills to disk, recall latency degrades by roughly an order of
magnitude, and the symptom is "search got slow" with no error anywhere.

Rough sizing at 1536-dimension embeddings:

| Vectors | Raw (float32) | Working set with HNSW | Practical RAM |
|---|---|---|---|
| 100 K | ~0.6 GB | ~1 GB | 4 GB |
| 1 M | ~6 GB | ~9 GB | 16 GB |
| 10 M | ~60 GB | ~90 GB | 128 GB, or shard |

Cross the line where the index no longer fits and the honest options are fewer
dimensions, quantisation, or sharding — not a faster disk. A faster disk makes a
disk-bound HNSW slightly less bad; it does not make it good.

## 4. Storage and retention

- **Database**: point-in-time recovery, retained ≥ 30 days. Memory and decision
  records are the product; a lost decision log cannot be regenerated by re-running
  anything.
- **Embeddings are derived** and may be rebuilt from source documents. Back up
  the documents; the vectors are a cache with an expensive miss.
- **Schemas** (`database/schemas/`) are versioned in the repository and applied
  in order. The test suite creates and drops its own database.

## 5. What this standard refuses

- **No GPU.** Inference is a provider's problem. If a code path needs a local
  GPU, that path belongs behind an API.
- **No hardware answer to a rate limit.** Provider throttling is not solved by
  a bigger machine, and treating it that way buys silence, not throughput.
- **No SKUs.** A class is a floor to clear, not a part number to match.
