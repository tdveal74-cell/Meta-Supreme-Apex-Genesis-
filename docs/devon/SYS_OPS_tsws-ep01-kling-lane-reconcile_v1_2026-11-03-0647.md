What the skills say, in the parts that govern spend. A build is an editable definition, `comfy-build.yaml`, written beside the install by `comfy build init`; a release is an immutable cut of it, made by `comfy build release create <install> --target linux/nvidia --watch`, and that line is the one that commits a release and spends a release slot; a slot is a count, and nothing on the build surface bills by time. `init` fills `pipDependencies` with the whole pip freeze of the source environment, so the first cut goes with that list emptied. Models enter the spec by a source URL and a digest, resolved with `comfy build refs resolve`, either uploaded from the machine or fetched by the builder. Deploying bills by time from the moment a deployment is serving: `up`, `start`, `run`, `promote` and `rollback` spend, `stop` pauses it and keeps the endpoint and the staged models, `--min 0` scales to zero and pays a cold start on each wake, `--min 1` stays warm and charges while idle, and every `run` is a fresh billed job, so a resubmit is a second charge the CLI cannot look up. `comfy run` and `comfy generate` embed partner nodes paid in comfy.org credits and fail closed in a non-interactive run with `spend_consent_required` unless `--allow-spend`, or `--yes` for `generate`, is passed; the skill says to pass either only after the human has approved the spend, which here is a card.

The SDK: `COMFY_CLOUD_BASE_URL` is `https://cloud.comfy.org` (`client.py` line 67) and the model router defaults to `https://api.comfy.org`; a serverless deployment and Comfy Cloud both take the key from the `api_key` argument or `COMFY_API_KEY`; a workflow with partner nodes carries the same key once more as `extra_data.api_key_comfy_org`, the field the VPS submit tool fills, so one comfy.org key serves every route.
