# DEVON Hermes Surface Sentinel v1

## Why

Tee asked that DEVON not miss any Hermes agent update.

DEVON's record of the Hermes agent is the capability table in
`SYS_OPS_devon-hermes-stack-status_v2_2026-08-25.md`, maintained by hand.
Before this arc, two things referenced that document and neither read its
inventory: `scripts/estate_reconcile.py` pinned three sentences about the
Alembic head, and `test_devon_console_gate.py` checked the honesty label.
So a new tool, route, table, column, state or migration could land with CI
green and the record silently stale. That is not hypothetical. It is what the
2026-09-02 audit found by hand, when this same document carried a superseded
schema head while production had moved past it.

The runtime side was checked and was already closed:
`ExpansionToolAdapter._ready` refuses a write when no durable writer is
injected, and `process_local_ok` defaults to `False`, so an update cannot
vanish into memory. This arc pins that invariant rather than rebuilding it.

## What shipped

`docs/devon/hermes-surface.json` is the manifest, generated from the code and
never hand typed. `test_devon_hermes_surface.py` re-derives the surface every
run and fails when the two disagree, naming the exact item that moved.

| slice | count | derived from |
|---|---|---|
| tools | 20 | `build_tool_registry()`, all six adapters, with risk class, reversibility and blast radius |
| routes | 24 | every v1 router whose prefix begins `/agent`, read from the routers, hidden routes included |
| columns | 126 | every agent table declared anywhere under `app/models` |
| states | 9 | the two expansion state machines |
| migrations | 7 | migrations touching a pinned agent table, each with its parent revision |

Two invariants hold independently of the manifest, so regenerating cannot
remove them: every HIGH_IMPACT tool stays irreversible and declares a blast
radius, and every expansion tool stays a WRITE. Both drive `registry.execute`
rather than a private helper.

The counts sit in one fenced `hermes-surface-counts` block in the Hermes
record and are read back out of it, so regenerating the manifest cannot clear
a red without moving the document a human reads.

The file runs in the standalone CI job: no database, no `PYTHONPATH`, 13 tests
in about two seconds.

## Three cycles, and what each one found

The first cut was scored by a fresh critic given only the deliverable and the
ask. It was wrong, and the second cut was wrong in narrower ways. Both are
recorded here because the pattern is the value.

**Cycle 1** landed three real Hermes changes with the sentinel green: a
HIGH_IMPACT irreversible browser tool, a `POST` route under `/agent-tasks`,
and a column on `agent_tasks`. It also deleted the durable writer guard from
`_spawn_subagent` and watched the whole 1552 test suite pass. Root cause: the
surface was counted from one adapter lane rather than from the estate, which
is the corollary already written in `CLAUDE.md` and the third time this estate
has been wrong in that direction. Two of the first cut's own tests were also
theatre: the invariant tests asserted against a private helper, so the guard
they claimed to hold could be deleted with everything green, and the ordering
assertion sorted the recorded side before comparing it, so it could never have
failed.

**Cycle 2** confirmed those fixes and found six more. The worst was silent:
`database/migrations/script.py.mako`, the generator `alembic revision`
actually uses, emits `revision: str = '020_x'` with a type annotation and
single quotes, and the parser matched only `revision = "020_x"`. A migration
created the repository's own default way was dropped without a word. A
migration in that shape adding `bypass_approval` to `agent_tasks` passed. So
did a new `/agent-runtime` router prefix, a route declared
`include_in_schema=False` that served 200 unauthenticated, an agent table
declared in a neighbouring model module, and a count launder that satisfied
the whole file regex from a scratch line while the paragraph a human reads
still said something else.

**Cycle 3** closed all of them and is what this document describes. It also
found one bug the critics could not: the route strings carried a doubled
prefix, because `route.path` already includes the router's prefix. The
manifest could not catch it, since the manifest is generated by the same
function it is checked against. Only reading the output caught it, which is
the standing argument for reading the artifact rather than the exit code.

## What it does not do

It pins the surface, not the behaviour behind it. It does not see a column
added by raw SQL under `database/schemas/` that no model declares, nor a
rewritten migration body under an unchanged revision. It reads the source
tree, so it says what the next deploy will apply and never what production
runs. The deployed estate stays the job of `scripts/estate_reconcile.py`, and
stays UNVERIFIED without a Railway read. The Status column of the capability
table is a human judgement and stays one.
